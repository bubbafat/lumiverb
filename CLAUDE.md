# Claude Code — Lumiverb repository guide

Navigation index. Read this before `ls`/`grep`/`find`. File paths and
ownership live here; logic, schemas, and thresholds do not — read the code.

---

## Stack & topology

Python 3.12 (FastAPI + SQLModel + Postgres 18 + Quickwit), React 18 +
Vite + TanStack web UI, Swift 5.9 / SwiftUI for native macOS + iOS
(shared `LumiverbKit` package, XcodeGen project).

FastAPI and the scheduler (`lumiverb-scheduler`, all processing, on the
same box) are the persistent services; only the scheduler and the CLI
scan; macOS and iOS are browse-only. Direction is ADR-016: one server (a Linux box, or a Mac) schedules all
processing against read-only storage, human data is never overwritten by derived data, and what used
to be "collections" are projects (`/v1/projects` for every client;
`/v1/collections` is gone). Quickwit sidecar with a
Postgres fallback. Auth: JWT (web) + API keys (CLI), both
`Authorization: Bearer <token>`; roles `admin` / `editor` / `viewer`.

## Top-level layout

```
src/
  server/                  Python API server, DB, search, upgrade runner, scheduler (all processing)
  producers/               One folder per producer: its spec and its work; the runner
  processing/              What the scheduler and the CLI's scan share (API client, scanning, media tools, AI machines)
  client/                  Python CLI (asks the scheduler; never processes)
  shared/                  Code used by both server and client
  ui/web/                  React web app (Vite)

  api/ cli/ core/ models/ repository/ search/ storage/ upgrade/ video/ workers/
                           ⚠️  STALE pre-ADR-014 __pycache__ shells. Ignore.

clients/lumiverb-app/      Native macOS + iOS (XcodeGen)
  Sources/macOS/  iOS/  LumiverbKit/      project.yml, Lumiverb.xcodeproj
clients/resolve/           DaVinci Resolve Studio Workflow Integration (prototype: search, add to bin / timeline)

tests/        Python tests (pytest)
migrations/   Alembic — control/ + tenant/ trees
scripts/      Ops (update.sh = one-command update, logged; release.sh vX.Y.Z = audit what it ships (audit_release.py: the formula's Python extras and npm build; stops at an advisory unless --accept-advisories), tag, GitHub release and the Homebrew tap's PR; deploy-*, update-*, migrate.sh, …)
docs/         Long-form docs + ADRs
quickwit/     Quickwit index schemas
```

Each chosen folder (previews', a library's, backups') gets a test write when chosen and again every few minutes for the Admin rows and Settings: `src/server/write_check.py`. | Server on its own machine (any platform) | `src/server/lifecycle/`: the `lumiverb-server` command. `envfile.py` reads the install's env file as systemd's EnvironmentFile does (one file for both platforms; launchd can't load it), `migrate.py` is migrate.sh's steps, `init.py` writes an install's env file (deploy-api.sh's, for Homebrew's PostgreSQL), Quickwit's config and the nginx site (deploy-api.sh's and deploy-web.sh's, held to the same bytes by `tests/test_server_init.py`), each only if it isn't there: Homebrew's post_install runs it on every upgrade. The install is always named (`--env FILE`, `$LUMIVERB_ENV_FILE`, or `CONTROL_PLANE_DATABASE_URL` in the environment), never assumed: on Linux `/etc/lumiverb/env` is prod's. `lumiverb-server run` is a Mac's one Homebrew service, the whole install: it starts what the env file names (`PG_BIN`: Lumiverb's own PostgreSQL, a cluster of its own made on first start, `postgres.py`; `QUICKWIT_BIN`; `NGINX_BIN` with its own whole config), migrates (waiting for that PostgreSQL), then `supervise.py` runs the API and scheduler (which folders it reads is the env file's `LUMIVERB_ROOT_MAP`, never assumed: a Mac's is `{"/": "/"}`, written by `init --local-roots`; it never reads the env file's folder, `LUMIVERB_REFUSED_ROOTS`; where it reads every folder, a library's folder is chosen only on that machine: `dependencies.require_folder_chosen_here`) (each child may wait for an event: `start_after`) as a Linux install's units do (env, restart delays, stop order and signals: only the scheduler's main process hears SIGTERM; one exiting soon after each start waits twice as long each time, up to 10 min), and `upkeep.py` posts what a Linux install's timers post (a 03:00 cleanup missed while asleep runs on waking; a first start waits for the first 03:00). When `brew upgrade` moves the opt link it was launched through, it stops everything and execs the new install (`watch_for_upgrade`), so an upgrade needs no restart. It makes its control database if it's missing, and logs (never prints: launchd's file would buffer it). Its log is launchd's file, rotated at 10 MB with 4 kept (`log.py`): each child's output comes through run, a line at a time, named (`api | …`, `quickwit | …`) and without colour codes; no web request lines (`--no-access-log`), Quickwit at warn, the API's own INFO lines (`src/shared/logging_config.py` `configure_api_logging`). The web app shows it at Admin › Logs (`src/server/service_log.py`, `routers/system.py` `/v1/system/logs`, `pages/AdminLogsPage.tsx`): a Mac's file (run tells the API where, `LUMIVERB_LOG_FILE`), Linux's journal once whoever runs the server adds the service user to `systemd-journal` (the whole system journal, so never the scripts: the page says how and what it opens). A Linux install stays on systemd + `scripts/update.sh`; a Mac (Homebrew) runs this instead |

## Running things

Standard incantations work (`uvicorn src.server.api.main:app --reload`,
`lumiverb <cmd>`, `npm run dev`, `swift test`). Non-obvious:

- **uv only** — no `pip`. Use `uv add` / `uv run` / `uv sync`.
- **macOS app** — `cd clients/lumiverb-app && xcodegen generate && xcodebuild -project Lumiverb.xcodeproj -scheme Lumiverb-macOS -configuration Debug build CODE_SIGNING_ALLOWED=NO`

## Tests

- Python: `uv run pytest -m fast` (no DB/AI), `-m slow` (testcontainers Postgres 18, `PG_IMAGE` in `tests/conftest.py`), `ai` (real inference, opt-in). Bare `pytest` runs fast + slow.
  Every failure is also appended, named and with its traceback, to `.pytest_cache/failures.log` (conftest), whatever happens to the run's output: a flaky test is never ignored, so it must never go unnamed. Every skip and xfail, with its reason, to `.pytest_cache/skips.log`: a test that skips itself only sometimes is coverage lost only sometimes (a test never skips because of what another test did: it makes its own data).
  `-n auto` runs it in parallel (pytest-xdist, a module's tests on one worker). One Postgres serves the whole run: `PostgresContainer` in a test is a fresh database on it, and the migration helpers clone a template migrated once (`tests/conftest.py` docstring; `LUMIVERB_TEST_PG_PER_MODULE=1` for a container per module).
  A test that needs a clip to try something else on makes it with `tests/clips.py` `make_clip` (ingest's own repository call); what a scan would do with a file, `tests/scan_plan.py` `scan_would` (a dry-run scan session); a photo's faces, `tests/faces.py` `plant_faces` (`batch-faces`, as the faces producer saves them); what the scheduler would hand out, `tests/producer_fakes.py` `due` (its queue).
  Quickwit is off for every test (conftest pins `QUICKWIT_ENABLED=false`, whatever `.env.local` says; mock `QuickwitClient` to test sync code). `uv run pytest -m quickwit` (opt-in) checks the real document builders against the real index schemas and search in a throwaway Quickwit in Docker (`tests/test_quickwit_real.py`).
  The install/update script tests (`test_update_script.py`, `test_deploy_scripts.py`) run only on Linux (`LINUX_INSTALLER` in conftest): the scripts use systemd, apt, flock and GNU sed, and a Mac installs with Homebrew.
- Swift: XCTest in `LumiverbKit`. **No macOS-target test bundle** — testable code must live in LumiverbKit.
- Resolve plugin: `node --test clients/resolve/test/` (no dependencies; fakes for `fetch` and Resolve).
- Web UI: `npx vitest run` in `src/ui/web` (Testing Library component tests sit beside their components), plus `npx tsc --noEmit -p .`. `src/test/setup.ts` gives tests jsdom's localStorage back: Node 25+'s own shadows it, undefined.

## API conventions (do not relitigate)

- All routes under `/v1/`, `Bearer` token required.
- Tenant from token, **never** a URL param.
- Cursor pagination only (`after` / `next_cursor`).
- Errors: `{"error": {"code", "message", "details"}}`.
- Multipart uploads. No webhooks, no source serving. Rate limiting only on login and password reset (`api/rate_limit.py`).
- Routes match in **definition order** — static before parameterized.
- **The API requires the user's say** for surprising outcomes: the request carries the choice (e.g. `remove_from_projects`, `with_clips`) or gets a 409 in the error envelope with the facts, so every client must ask (`api/errors.py` `DecisionRequiredError`; cursor-api.md "Decisions the API requires").
- Deleting goes delete → trash → restore | delete forever, for assets and projects (libraries have a trash, no restore yet).

## Gotchas

- **`active_assets` view** must be dropped + recreated when adding columns to `assets`.
- **`app.routes` holds an included router as one entry** (FastAPI 0.143+): a test that checks every route walks them with `tests/app_routes.py` `api_routes(app)`, never `app.routes` alone (which finds none and checks nothing). FastAPI is `fastapi`, not `fastapi[standard]` (it brings OpenTelemetry's exporter), and its telemetry is off (`main.py` `NO_TELEMETRY`; `tests/test_no_telemetry.py`).
- **ONNX Runtime leaks ~35 MB/inference.** Batch work is subprocess-isolated for exactly this reason — don't collapse it.
- **`ThreadPoolExecutor`**: never submit all futures at once; cap at `concurrency * 2` and `_drain()`.
- **`systemd` units**: `update.sh` (its `update-api.sh`) writes the scheduler's (when the install does processing) and the upkeep timers' units afresh but only patches the API's and Quickwit's: an entry-point change there needs the unit fixed by hand (or `deploy-api.sh` run again).
- **Prod**: never SSH or run commands on the VPS. User handles deploys; server auto-updates after push.
